Migration guide

Start with the extension you ship. End with an unpacked MV3 copy you can inspect, load, and test.

Prepare the input

Point the CLI at a directory with an MV2 manifest. The converter discovers scripts from manifest entries, including a script-only background page when present. If you use a bundler, build the extension first. The converter copies packaged files, so keep unrelated project files and secrets out of this directory.

The output directory must not exist yet; its parent must exist and sit outside the input tree (or be the input’s parent). Use another fresh output directory for a second conversion.

What converts?

A direct, top-level blocking registration with literal filter data can become an always-enabled rule. For example, this callback has a decision Chrome can make ahead of time:

background.js · MV2 input
chrome.webRequest.onBeforeRequest.addListener(
  details => ({ cancel: details.method === 'POST' }),
  { urls: ['https://example.org/beacon/*'] },
  ['blocking'],
);

The resulting DNR rule blocks POST requests matching that URL pattern. Other methods continue normally. Chrome evaluates the rule without calling into the worker.

Cancel or redirect
Use an inline callback returning { cancel: true }, an absolute HTTP(S) redirectUrl, or a supported uppercase method equality as above. Use literal listener flags and URL patterns.
Observe a request
Keep direct nonblocking listener registrations. They receive native Chrome event details, including completion and error events.
Answer an auth challenge
An inline blocking onAuthRequired handler becomes an asyncBlocking callback. The converter adds the auth provider permission.
Use settings, edit headers, or inspect the body
These need an explicit port. Update a rule store when settings change, describe headers as edits, and use an observer for body inspection. MV3 doesn’t offer arbitrary body-dependent blocking.

Popups & content scripts

The CLI reads packaged script tags in the manifest’s browser-action popup, options pages, DevTools page, and Chrome URL override pages. Both classic and module entry scripts keep running in their original page, with access to its DOM. Only the referenced entry files are inspected. Move executable inline scripts and HTML event handlers into local files.

For a popup that talks to the current tab, tabs.sendRequest becomes tabs.sendMessage. A corresponding listener in content_scripts[].js moves from extension.onRequest to runtime.onMessage. See the working popup example.

Use runtime messaging to replace direct access to a background page. Move privileged operations out of content scripts and handle them in an extension page or worker. Blocking listeners in UI or shared scripts require a manual port, since their lifetime depends on where they are registered.

Tab injection

Direct chrome.tabs.executeScript, insertCSS, and removeCSS calls in background or UI scripts move to chrome.scripting. Pass an explicit tab ID and an inline details object. The converter adds the scripting permission; existing host access or a user-granted activeTab is still required.

background.js · MV2 input
chrome.tabs.executeScript(tab.id, { code: 'document.title' }, titles => {
  console.log(titles);
});

A fixed JavaScript string becomes a packaged file. The callback still receives values rather than frame metadata. A CSS string becomes css; a packaged filename becomes a one-element files array. Literal frame selectors and CSS origin are translated.

For computed JavaScript strings use a packaged function and arguments. For precise injection timing consider a registered content script. Implicit tab IDs and matchAboutBlank: true require manual migration. Other tab methods such as tabs.query remain available.

Inspect the output

manifest.json
The manifest declares MV3 and, for extensions with a background entry, a service worker. Required and optional host patterns move into their respective host permission lists. A browser action becomes an action. A legacy options page becomes options_ui with open_in_tab: true.
webrequest-mv3-worker.js
A classic worker imports the copied background scripts in manifest order. Direct browser-action references become chrome.action. Legacy extension messaging and URL helpers move to chrome.runtime, while tab-directed sendRequest becomes tabs.sendMessage.
webrequest-mv3-rules.json
Created when static rules are extracted. The manifest enables the ruleset; each migrated registration is marked with its rule ID in the copied script.
Check the rest of the extension. Review module dependencies, dynamically loaded scripts, frames and pages selected at runtime separately. A worker has no DOM or localStorage, and its globals can disappear between events.

Use a build script

Install the Node entry point in your build project, outside the extension you package.

Terminal
npm install --save-dev github:x7k6/webrequest-mv3
build.mjs · Node.js
import { migrateExtension } from 'webrequest-mv3/migrate';

const { outputDir, ruleCount } = await migrateExtension(
  './my-extension', './my-extension-mv3'
);
console.log(outputDir, ruleCount);

Run node build.mjs. The promise resolves after the copy is ready, or rejects with a diagnostic. The build-time parser is not included in the extension.

Verify in Chrome

To exercise the converter with a small fixture, run these commands from a checkout of the repository:

Terminal · repository root
npm ci
node bin/webrequest-mv3.js examples/legacy ../legacy-mv3
npm run demo
  1. In chrome://extensions, enable Developer mode and load legacy-mv3 unpacked.
  2. Open http://127.0.0.1:8765/webrequest-mv3/. Blocked navigation should show ERR_BLOCKED_BY_CLIENT.
  3. Follow Redirect. You should land on the headers page. Pin the extension to see the observer set the status badge to 200.

The legacy fixture has no header edits. To test those too, disable the converted fixture and load the repository’s MV3 example. Its headers page echoes X-Demo-Request: MV3.

Troubleshooting

The CLI reports a file and line number.

Check that the registration is direct, the blocking callback is inline, and the filter is literal data. A callback that reads runtime state or has side effects cannot be extracted. Move notifications into observe() and use a rule store for settings-driven decisions.

The output directory already exists.

Pick a new sibling directory. The converter refuses to overwrite an existing directory, even an empty one.

The extension loads, but the rule doesn’t fire.

Check the target and initiator host permissions, Chrome’s site-access setting, and the rule’s URL pattern, resource types, and method. See URL matching. For generated rules, inspect the static rules file rather than querying dynamic rules.

My extension uses an HTML background page.

The CLI reads background.page and imports classic local <script src="…"> files in document order. Relative paths resolve from the HTML file, and the generated worker lives in that directory. Use plain script tags: inline code, modules, custom loading attributes, DOM elements and page event handlers require a manual port. Review code that accesses the old page through getBackgroundPage().
